# wheel fix：用社群與輪子輔助修復

`/wheel fix <症狀或錯誤原文>`。只補強「找解法」這一段：別人是否遇過同一問題、有沒有現成修法或輪子。重現、根因、驗收照你自己的除錯流程做，這裡不取代它。

1. **舊帳**：§0 `find`，關鍵字用錯誤原文的片段＋一組英文。命中且修法對得上這次錯誤原文 → 照做，停。
2. **驗元件歸屬**：錯誤訊息出自哪個行程或套件，就去查那個元件的上游；不是你的宿主、也不是你以為的那個。
3. **社群軸（逐字查）**：`gh search issues "<錯誤原文>"`（不限 closed）、`gh search prs` 找未合修補，再用去掉專有名詞的通用說法與一組英文各查一次。讀留言，workaround 與根因多在留言。HN、Stack Overflow 照 §3。
4. **對版本**：問題從哪版出現、哪版修（release notes）。上游已修 → 升版；有 workaround → 照做；上游判定為服務端問題 → 根因在上游，本機只做繞道。
5. **輪子軸（只在要加依賴、換方案、自造 wrapper 時跑）**：找現成的 patch、wrapper、plugin，看採用量、授權、維護，裁決照 §5。
6. **採用前實測**：社群說法不等於實際行為。用最小重現確認「該被修的路徑確實修了、不該觸發的路徑沒觸發」；要歸咎某因素前，先在同時段跑一份無變因基準。
7. **輸出**：輪子卡首行 `輪子：`，卡片加一行 `修法來源：<issue／PR／release URL>`。實測過才登記 registry；被實測推翻的補一張「不做」更正卡。

同一修法失敗兩次 → 照 §6.5，停手重述假設，不試第三種變體。
